SHIFT · deployment reference · one page

Who talks to whom, and what you actually have to install

SHIFT is hub-and-spoke. A hub holds the control plane, runners execute flows and touch your data, and an optional gateway is the only thing that ever accepts an inbound request. This page is the whole communication picture and the install order that follows from it.

The rule everything else follows

Nothing at the edge ever initiates a connection inward.

Runners dial the hub. Runners dial the gateway. The hub dials the gateway. Nothing dials a runner, and nothing at the edge dials the hub — so the boxes closest to the internet hold no database connection, no encryption key and no credential worth stealing.

The three components

Hub hubd

required

Control plane: identity, the flow designer, the durable task queue, the connector registry, schedules and audit. Needs PostgreSQL. Never sees your payload data.

:8400 · loopback by default

Runner runnerd

required

Executes flows, streams the data, runs connectors as subprocesses. Stateless and disposable — run one or fifty. This is the only component that touches your systems and your records.

:8340 · loopback by default

Gateway gatewayd

only for inbound

Accepts public HTTP requests and hands them to an available runner. Holds no database, no keys and no queue. Absent by default — and if you have no inbound traffic, you never install it.

:8443 public · :8444 control

Connectors are not a fourth component. They ship as signed binaries the runner launches as local subprocesses over a unix socket, and they never listen on a network port.

Do you need a DMZ? Do you need a gateway?

DMZ — not required

The gateway is deployable into a DMZ, and that is the strongest posture because the box in the DMZ holds nothing worth taking. But it is a placement, not a requirement. Put it on your private network behind an existing load balancer and everything works identically.

Nothing in SHIFT assumes a DMZ exists. If you have no inbound traffic at all, there is no edge to harden — see the pull-only shape below.

Gateway — required for web requests

Runners bind privately in every deployment. They do not accept connections from callers, and that is deliberate rather than a limitation. So if something outside needs to call a flow — a webhook, a partner API, an app — a gateway is how the request reaches a runner.

No gateway means no inbound path. Flows still run on schedules, on polls, and on the hub queue.

Three deployment shapes

Pull-only

hub + runners

Schedules, polling sources, queue-driven work. Zero inbound attack surface — nothing in the deployment accepts a connection from outside. No gateway installed.

Gateway, no DMZ

+ gateway, private

Gateway on the private network behind your existing ingress or load balancer. Inbound flows work. Common for internal APIs and for teams without a DMZ to deploy into.

Gateway in a DMZ

recommended for public

The public internet calls your flows. The DMZ box holds no database, no encryption key, no user secret and no durable payload — losing it loses nothing.

Install order

Sequential because each step hands the next one a credential. Nothing works out of order.

  1. Hub — the only thing that needs a database

    Point it at PostgreSQL; it runs its own migrations. Configure OIDC for humans, and keep the break-glass admin token for the first login. 

    # control-plane certificate authorities — the hub is the only signer
hubd \
  -db "postgres://…" \
  -listen 0.0.0.0:8400 \
  -runner-ca-cert  runner-ca.pem  -runner-ca-key  runner-ca-key.pem \
  -gateway-ca-cert gateway-ca.pem -gateway-ca-key gateway-ca-key.pem

    The runner CA and gateway CA are separate on purpose: a runner certificate must never authenticate anything on a gateway, and the reverse.

  2. Runners — one single-use token each

    Mint a registration token in the hub, hand it to the runner by environment variable, and the runner generates its own private key and gets a short-lived certificate back. The key never leaves the runner and the token is spent on first use. 

    # token by env, never a flag — flags show up in process listings
SHIFT_HUB_REG_TOKEN=srt_… \
runnerd \
  -hub https://hub.example:8400 \
  -name edge-runner-1 \
  -cred-file /var/lib/shift/hub.cred

    Add -gateways https://gw.example:8444 once a gateway exists, so this runner also polls it for inbound work. Repeat for as many runners as you want; they need nothing from each other.

  3. Gateway — only if you need inbound

    Start it with no configuration at all. It comes up inert: no routes, no certificates, serving nothing but a public key fingerprint printed to its own log. 

    gatewayd -public :8443 -control 0.0.0.0:8444

{"event":"gateway.awaiting_adoption",
 "fingerprint":"9f2c…a11b"}

    Copy that fingerprint into the hub along with the gateway's URL. The hub then dials the gateway and accepts it only if the key matches — so the value you carried by hand is what establishes trust. Adoption then closes, and a restart comes back already adopted.

Firewall rules you actually need

RuleNeeded whenNote
runners → hub :8400 always outbound from the runner network
runners → your systems always whatever your flows talk to
internet → gateway :8443 inbound flows terminate TLS upstream if you prefer
hub → gateway :8444 inbound flows must not be TLS-terminated in between
runners → gateway :8444 inbound flows same port, same passthrough requirement

The control port carries certificate material and is verified by pinning the gateway's key, so an appliance that terminates it would be the thing the hub trusts instead of the gateway. If one sits in that path, forward the port at L4 rather than inspecting it. The public port has no such constraint — terminate it wherever you like.

What never happens

  • Your payload never reaches the hub. Records stream runner-side. The hub sees counts, timings and step names.
  • Secrets are never in the queue. A task carries {"$secret":"name"}; the runner resolves it at execution and never logs the value.
  • The gateway stores nothing. No database, no encryption key, no user secret, no durable payload. No runner available means a clean 503, never a queue.
  • Nothing at the edge dials inward. Not during adoption, not at startup, not on renewal.
  • No shared filesystem. Runners coordinate through the hub's queue, never through disk.
